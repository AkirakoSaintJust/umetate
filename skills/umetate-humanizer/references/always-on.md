# Always-on writing rules

Copy one of these blocks into a project's standing instructions when you want the
voice on by default. The skill is still the full method, and these blocks are the
short version.

## For `AGENTS.md` or project instructions

```markdown
## Writing rules

When you write prose, docs, commit bodies, or messages:

- Start with the thing, the cause, or the constraint. Do not introduce it by
  saying what it is not.
- A negation earns its place only when it carries a causal link, a factual
  comparison, a counterintuitive explanation, a real limit, or a correction.
  Otherwise cut it.
- Do not write "A, not B" as an adversative. Use "rather than", a separate
  sentence, or a "but" clause.
- Do not add a `what this is` section. The reader is already using the thing.
  Spend the words on the next action, the controls, or a real limit.
- No lists where every item starts with `The`. Drop the article, lead with the
  noun or verb, or write the list as prose.
- No wh-word headings or table labels. Use a noun phrase or an imperative:
  `Get started!`, `Navigation`, `Functionality`.
- No counted-couplet headings, captions, or table descriptions. Name the section
  and put the count in the body.
- Do not put raw storage values in a user document. Show the value and range the
  panel shows.
- Join a fact to its cause, condition, or specification. Use a relative clause,
  "with" and a colon, "only when", and "so" or "because".
- No aphorisms and no summary verdicts. End on a concrete fact, an instruction, or
  a specific judgement.
- No em dashes, no semicolons, no marketing adjectives, no heading chains, no false
  dichotomies, no negative parallelism.
- No bare `claim` for a feature. Write `claimed feature`, or name the feature.
- No `source of truth`. Write `only reference` or `single reference`.
- No `I built` for a thing you made. Write `I made`. Keep `built` for a compiled
  binary or a CI job.
- No `dogfood`. Write `test project made from our own readymade components`, then
  `the test project`.
- No `lives in` for a file, folder, sub-project, document, or component. Write `is in
  the PATH folder`, `is stored at`, or `PATH's path within the repo is`.
- No `gap` for missing work. Name the missing work, the missing feature, the bug, the
  oversight, or the problem.
- Measure the prose with the rhythm gate for its register. Check the mean, median,
  and spread, not only the mean.
- Keep the author's first person, contractions, dry asides, light UK slang, and
  self-description. Fix grammar, not voice.
- Do not invent a model, date, number, or quote.
```

## For a system prompt

```
Write like a specific builder and player, not a committee. Start with the thing,
the cause, or the constraint. Join facts to their causes and conditions. No em
dashes, no semicolons, no aphorisms, no marketing adjectives, no negative
parallelism, no "A, not B" adversatives. No product self-description sections.
No article-drumbeat lists. No wh-word headings. No counted-couplet headings,
captions, or table descriptions. No raw storage values. No bare claim, no
`source of truth`, no `I built` for a made thing, no dogfood, no `lives in` for a
location, and no `gap` for missing work. Measure the prose with the rhythm gate for
its register, and check the median and spread as well as the mean. End on a concrete
fact, an instruction, or a specific judgement. Preserve the author's contractions,
asides, and UK slang. Never invent a fact.
```

## The one-line version

> State the thing. Join the cause. Cut the slogan, the product description, and the article drumbeat. Keep the voice.
